# Технічні рішення (ADR)

Тут ви фіксуєте рішення своєї реалізації, які вимоги PM свідомо залишають відкритими: модель даних, політики RLS,
структура сторінок, бібліотеки. Продуктові рішення (що робить система) — не тут, а у вимогах PM: відповіді на issues
«Питання до вимог» у його репо і «Журнал змін» вимог (знімок — `requirements/`, приносить `/requirements-sync`).
PM наприкінці порівнює реалізації розробників команди: ADR з AC ID — найкоротший шлях пояснити, чому ваша реалізація
саме така.

- Один файл — одне рішення: `docs/decisions/NNNN-коротка-назва.md` (`0001-model-leave-entries.md`).
- 1–2 сторінки. Старі рішення не видаляємо: нове рішення отримує статус «замінює NNNN», старе — «замінено NNNN».
- Посилайтесь на AC ID, яких стосується рішення.

## Рішення, успадковані з WS6

Архівний план `openspec/changes/archive/2026-10-21-impl-leave-ws6/design.md` не редагуємо, але в кількох місцях
реалізація від нього відійшла. Наступна зміна (`design.md` нового `impl-<зріз>`) починає звідси, а не з архівного
плану, — щоб не повернути відкинуте рішення, наприклад не продублювати правила доступу в TS.

| Було в плані WS6 | Стало | AC | Рішення |
|---|---|---|---|
| D5: чиста `access.ts` — хто бачить чиї записи й залишки | — (у базі): view `public.my_leave_records` (`security_invoker`) і RLS на `public.leave_records`; черга менеджера — `private.decision_records()`; залишки — `private.can_view_balances` у `private.get_balance_inputs`, список працівників — `private.balance_employees()` (`private.manages_employee` або роль `admin`) | AC-LEAVE-14, AC-DECIDE-01, AC-BALANCE-12, AC-BALANCE-13, AC-BALANCE-20 | ADR 0002, ADR 0003 |
| D5: тест `access.ts` | DB-тести на PGlite з роллю `authenticated` — перевіряють те, що віддає база, а не копію правила | ті самі | ADR 0001 |

Правило для нових зрізів: право доступу живе в одному місці — у базі (RLS, view з `security_invoker` або перевірка
першим кроком у функції `security definer` схеми `private`); сторінка лише показує відмову, а тест іде через PGlite.

## Відкрите для WS10

Не рішення, а знахідки, з яких почнеться `design.md` зрізу WS10 (керування користувачами). Кожна — кандидат в ADR.

### Зміна email через Supabase Auth обходить правило «ім'я та email змінює лише адміністратор»

- Рев'ю WS7 (п. 2), питання PM mkozlovskyi-ops/course-staff-management-spec#19 (Q6).
- **Що є.** Колонкові права (`20261026181152_profiles_name_admin_only.sql`) не дають працівнику змінити
  `public.profiles.email`, тест — `tests/db/profiles.test.ts`. Але логін — `auth.users.email`, і
  `supabase.auth.updateUser({ email })` з публічним ключем змінює його повз `profiles`.
- **Що робить Auth (перевірено читанням коду, не прогоном).** `supabase/auth`, `internal/api/user.go` (коміт `3afa027`,
  2026-08-06): автопідтвердження («Confirm email» вимкнено, `enable_confirmations = false`) діє лише для анонімних
  користувачів — «permanent users always need to verify their email address when changing it». Для teacher1@ Auth
  лише надсилає лист підтвердження (`double_confirm_changes = true` — на стару й нову адресу); логін змінюється після
  переходу за посиланням. Отже, **одразу** email не зміниться, але працівник із доступом до пошти зможе змінити свій
  логін сам — правило матриці цього не забороняє.
- **Наслідки.** (1) Після підтвердження `profiles.email` лишиться старим: тригер `on_auth_user_created` — лише
  `after insert`, оновлення `auth.users` не синхронізується. (2) Адреси `*@example.test` листів не отримують, а
  вбудований SMTP шле лише учасникам проєкту, тож на тестових акаунтах зміна не дійде до кінця — перевірити поведінку
  можна лише на локальному Supabase (`npx supabase start`, Inbucket) або з власним SMTP.
- **Варіанти на WS10 (не обрано).** Заборонити самостійну зміну email на боці Auth (чи є для цього налаштування чи хук — перевірити); змінювати email
  лише адміністративним API (`auth.admin.updateUserById`) із серверної дії адміністратора; синхронізувати
  `profiles.email` тригером `after update of email on auth.users`. Вибір — після відповіді PM на Q6 і локальної перевірки.
