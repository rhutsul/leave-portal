# 0003. Доступ до залишків перевіряє `get_balance_inputs`, а не `access.ts`

- Статус: прийнято
- Дата: 2026-10-21
- AC: AC-BALANCE-12, AC-BALANCE-13, AC-BALANCE-20

## Контекст

Вимога `requirements/03-leave-balance.md`: працівник бачить лише власні залишки (AC-BALANCE-13); відповідальний
менеджер будь-якої посади працівника — повний залишок, ті самі числа, що бачить працівник (AC-BALANCE-20,
mkozlovskyi-ops/course-staff-management-spec#6); менеджер без жодної посади працівника — нічого (AC-BALANCE-12);
адміністратор — усіх.

План (D5 `openspec/changes/impl-leave-ws6/design.md`, задача 3.2 `tasks.md`) відводив це правило чистій функції
`access.ts`, а дані — функції бази `get_balance_inputs` (D4), яка працює як `security definer` і RLS не підлягає.
Тобто функція бази в будь-якому разі мусить перевіряти право сама: інакше будь-хто, хто ввійшов, отримав би залишки
будь-кого через Data API. Чиста `access.ts` тоді лише копіювала б ту саму перевірку, і тест перевіряв би копію, а не
те, що насправді віддає база — та сама причина, з якої ADR 0002 відмовився від `access.ts` для «My requests».

## Рішення

- `private.can_view_balances(employee_id)` у міграції `20261020214031_balance_inputs.sql`: сам працівник,
  `private.manages_employee` (менеджер хоча б однієї посади працівника) або роль `admin` з `profiles.role`.
- `private.get_balance_inputs` перевіряє це право першим; без права — `42501 Balances are not available` (той самий
  код для неіснуючого працівника, тож відповідь нічого не розкриває). Сторінка `/balances` на цю помилку показує
  «These balances are not available to you» замість залишків.
- Список працівників для вибору на `/balances` — `public.balance_employees()` з тим самим правилом (RLS на `profiles`
  показує лише власний профіль, тож імена інших — лише звідси).
- Тести — `tests/db/balances.test.ts` на PGlite (ADR 0001): AC-BALANCE-12, AC-BALANCE-13, AC-BALANCE-20 викликають
  саме ту функцію, яку викликає сторінка.
- `access.ts` для залишків не створюємо. Формула залишку лишається чистою функцією `src/lib/leave/balance.ts` (D5).

## Розглянуті варіанти

- `access.ts` + перевірка в базі — два місця для одного правила; тест чистої функції не помітить, якщо міграція
  змінить перевірку бази.
- Лише `access.ts` у server component перед `rpc` — небезпечно: `get_balance_inputs` доступна через Data API напряму.
- RLS-політики на `leave_records` замість `security definer` — менеджер додаткової посади не бачить записів основної
  посади (AC-DECIDE-01), а повний залишок йому потрібен (AC-BALANCE-20); тому функція віддає лише підсумки по датах.

## Наслідки

- Правило «хто бачить залишки» живе в одній функції бази й перевіряється на справжньому Postgres.
- `/decisions` (задача 4) використовуватиме той самий `get_balance_inputs` для попередження менеджеру — право вже є.
- Зміна правила (наприклад, адміністратор WS10) — нова міграція з `create or replace function
  private.can_view_balances`.
