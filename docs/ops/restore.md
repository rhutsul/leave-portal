# Резервна копія бази і відновлення

Безкоштовний Supabase резервних копій не робить і не дає їх завантажити, тому єдина копія прод-бази — та, що робить
workflow `backup` (`.github/workflows/backup.yml`). Взято з матеріалів курсу:
[`materials/ops-kit/bonus/backup.yml`](https://github.com/koldovsky/2026-quitcode-11-devops-operations-hw/blob/main/materials/ops-kit/bonus/backup.yml)
і [`bonus/restore-drill.md`](https://github.com/koldovsky/2026-quitcode-11-devops-operations-hw/blob/main/materials/ops-kit/bonus/restore-drill.md);
відмінності від зразка — у розділі «Що змінено відносно зразка курсу».

> Копія, яку жодного разу не відновили, — не копія, а надія. Тому нічний прогін `backup` і ручний з увімкненим
> `restore_drill` (за замовчуванням) ще й відновлюють копію в одноразову базу й звіряють кількість рядків. Ручний
> прогін з `restore_drill` = вимкнено лише робить копію, без перевірки.

## Що робить workflow

| Job | Що робить | Що бачить журнал |
|---|---|---|
| `dump` | `supabase db dump` (CLI 2.120.0 з `package-lock.json`) через `SUPABASE_DB_URL`: `roles.sql`, `schema.sql`, `data.sql` (разом зі схемами `auth` і `storage`), окремо `data-public.sql` (лише `public`); дампи — окремі з'єднання, тому версію останньої міграції читає до й після них і, якщо `db-deploy` встиг застосувати міграцію, знімає все заново (до 3 спроб, далі червоний без артефакту); рахує рядки кожної таблиці з блоків `COPY`; пакує в `tar.gz` і шифрує `gpg --symmetric --cipher-algo AES256` фразою `BACKUP_PASSPHRASE`; відкриті файли видаляє; артефакт `supabase-backup` — лише `backup-<дата>.tgz.gpg`, 7 днів | розміри файлів, кількість таблиць |
| `restore-drill` | за розкладом або з `restore_drill` = увімкнено: `supabase db start` + `supabase db reset --local --no-seed` — одноразова база в раннері з міграцій репо (як `db-check`), адресу якої дає `supabase status`; розшифровує копію, у тій самій транзакції очищає таблиці дампу (міграції самі вставляють рядки) і завантажує дані з `session_replication_role = replica` — типово лише `public` (`data-public.sql`), `all` (`data.sql` разом з `auth.*`) лише явним вибором у Run workflow; порівнює кількість рядків кожної таблиці з копією | таблиця «від міграцій (очищено) / у копії / відновлено» в Summary прогону; червоний, якщо хоч одна таблиця не збіглась |

Коли: щодня о 01:41 UTC (≈ 03:41 за Києвом) і вручну. Цільовий **RPO** (скільки даних можна втратити) — 24 години.
Це ціль, а не гарантія: фактичну втрату визначає вік останньої придатної копії, тож якщо нічний `dump` впав, вона
більша — червоний прогін `backup` треба повторити вручну того ж дня.

Чому відкритого дампу ніде немає: у даних є e-mail і хеші паролів (схема `auth`), а артефакти публічного репо може
завантажити кожен, хто має доступ на читання. Тому в артефакті лише шифротекст, журнал не друкує вмісту, помилки `psql`
обрізаються до першої лапки, секрети — лише в `env` кроків, що їх використовують (сторонні дії їх не бачать), а
`restore-drill` не отримує `SUPABASE_DB_URL` взагалі.

## Секрети

Обидва — секрети середовища `production` (Settings → Environments → `production` → Environment secrets):

- `SUPABASE_DB_URL` — уже є для `db-deploy`: рядок Session pooler, порт 5432;
- `BACKUP_PASSPHRASE` — довга випадкова фраза (згенерувати в менеджері паролів). Зберігати **у двох місцях**: у
  менеджері паролів власника репо і в секреті середовища. Втратили фразу — жодної копії не розшифрувати.

Середовище `production` дозволене лише гілці `main`, тож запуск з іншої гілки секретів не отримає.

## Як запустити копію

1. Задати `BACKUP_PASSPHRASE` (розділ вище) — один раз.
2. Actions → **backup** → Run workflow, гілка `main`: `restore_drill` увімкнено, `scope` = `public` (типово).
3. Дочекатися зеленого прогону: в артефактах — `supabase-backup`, у Summary — таблиця рядків.

Розклад запускає workflow лише з `main`. Якщо в публічному репо 60 днів не було комітів, GitHub вимикає розклад —
тоді Actions → backup → Enable workflow.

## Як розшифрувати й відновити локально

Потрібні Docker, `gpg`, `psql` і Supabase CLI цього репо (`npx supabase` — версія з `package-lock.json`, не
`@latest`). Усе — лише проти **локальної** бази.

> **Передумова.** Крок 3 скидає локальну базу Supabase цього checkout (і будь-якого іншого з тим самим `project_id`
> у `supabase/config.toml` — контейнери спільні). Якщо в локальній базі є потрібні вам дані, зупиніться тут: окремий
> worktree не ізолює базу. Регулярну перевірку копії й так робить `restore-drill` у CI; локально відновлюємо лише тоді,
> коли треба подивитися дані копії.

1. Завантажити артефакт у тимчасову теку поза репо (відкриті файли не повинні потрапити в git) і запам'ятати її
   абсолютний шлях — далі команди йдуть із checkout:

   ```bash
   BACKUP_DIR="$(mktemp -d)"
   gh run download <run-id> -n supabase-backup -D "$BACKUP_DIR"   # або сторінка прогону → Artifacts
   ```

2. Розшифрувати (фраза — з менеджера паролів; `gpg` спитає її сам, у командний рядок не вписувати):

   ```bash
   gpg -o "$BACKUP_DIR/backup.tgz" -d "$BACKUP_DIR"/backup-*.tgz.gpg
   tar -xzf "$BACKUP_DIR/backup.tgz" -C "$BACKUP_DIR"
   # тепер $BACKUP_DIR/backup/: roles.sql, schema.sql, data.sql, data-public.sql, data.counts, data-public.counts
   ```

3. З кореня checkout підняти одноразову локальну базу з міграцій репо без сиду й узяти її адресу в CLI:

   ```bash
   npx supabase db start
   npx supabase db reset --local --no-seed
   LOCAL_DB="$(npx supabase status -o env | sed -n 's/^DB_URL="\{0,1\}\([^"]*\)"\{0,1\}$/\1/p')"
   ```

4. Завантажити дані — `data-public.sql` (лише `public`, як у CI); `data.sql` (разом з `auth.*`) на локальну базу
   CLI не лягає (розділ «Схема `auth`»). Міграції самі вставляють рядки (довідник `divisions` тощо), тож спершу, у
   тій самій транзакції, очистити рівно ті таблиці, що є в дампі, — інакше `duplicate key`:

   ```bash
   { printf 'TRUNCATE TABLE '; cut -d'|' -f1 "$BACKUP_DIR/backup/data-public.counts" | paste -sd, -; printf ';\n'; } \
     > "$BACKUP_DIR/truncate.sql"
   psql "$LOCAL_DB" --single-transaction -v ON_ERROR_STOP=1 -c 'SET session_replication_role = replica' \
     -f "$BACKUP_DIR/truncate.sql" -f "$BACKUP_DIR/backup/data-public.sql"
   ```

5. Звірити кількість рядків із підсумком **того самого** дампу (формат `таблиця|рядків`), як це робить
   `restore-drill`: `data.sql` → `data.counts`, `data-public.sql` → `data-public.counts`.
6. Після перевірки — `rm -rf "$BACKUP_DIR"` і `npx supabase stop --no-backup`.

## Справжнє відновлення після інциденту

Лише рішення людини, лише за офіційною інструкцією Supabase «Backup and restore using the CLI»: порядок `roles.sql` →
`schema.sql` → `data.sql`, у **новий** проєкт, а не поверх живих даних. Схему брати саме з `schema.sql` копії, а не
міграціями репо: міграції вставляють власні рядки (довідник `divisions` тощо), і `data.sql` поверх них впаде на
`duplicate key` (так упав прогін 44317599432). Перевірити, що в `supabase_migrations.schema_migrations` нового
проєкту є версії міграцій `main`: якщо таблиця порожня, `db-deploy` спробує застосувати всі міграції наново й упаде —
історію вирівнює `supabase migration repair`, і робить це лише людина (README). Після цього перемкнути все на новий
проєкт:

1. у Vercel (Production і Preview) — `NEXT_PUBLIC_SUPABASE_URL` і `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` нового
   проєкту, потім Redeploy: без нового API URL застосунок і далі ходить у старий проєкт;
2. у GitHub — новий `SUPABASE_DB_URL` у середовищі `production` (його беруть `db-deploy` і `backup`);
3. перевірити `/api/health` проду (`schema` — версія останньої міграції `main`), увійти синтетичним користувачем і
   відкрити «My requests»; потім у дашборді **нового** проєкту Supabase → Logs → API знайти ці запити (час і шляхи
   `/auth/v1/…`, `/rest/v1/…`). `/api/health` і вхід самі по собі пройдуть і зі старим проєктом — доказ перемикання
   лише журнал нового. Секретів і даних із журналу нікуди не копіювати.

Агент цього не робить. `supabase db push` з ноутбука, `supabase db reset --linked`,
`supabase migration down` проти справжнього проєкту — ніколи: вони розходяться з `main` або знищують дані.

## Що перевіряє тренування і чого не перевіряє

Перевіряє: копія розшифровується фразою з секрету; дані лягають на схему, зібрану з міграцій `main`, однією
транзакцією без помилок; у кожній таблиці стільки ж рядків, скільки в копії. Рядки, які вставили самі міграції,
тренування в тій самій транзакції спершу видаляє (`TRUNCATE` рівно таблиць дампу), тож «відновлено» — лише рядки
копії; скільки їх було від міграцій — окремою колонкою в Summary. Розбіжність схеми проду й міграцій
`main` (наприклад, DDL повз CI) тренування виявить, лише якщо вона заважає імпорту (інша колонка, обмеження) або
змінює кількість рядків; схем воно не звіряє — зайвий індекс чи політика на проді пройдуть непомітно.

Не перевіряє: вміст рядків (лише кількість), `roles.sql` і `schema.sql` (схему бере з міграцій, а не з дампу), файли
Storage (у проєкті їх немає, а дамп містить лише метадані), повну узгодженість `schema.sql` і `data.sql` (див.
«Обмеження»).

## Обмеження

- **Схема `auth` не відрепетирувана.** Перший ручний прогін 18.11.2026 (run 44316353788): `dump` зелений,
  `restore-drill` зі `scope=all` упав на `data.sql` з `ERROR: column …` у таблиці `auth.*`. Причина — схему `auth`
  створює GoTrue, і його версія в локальному Supabase CLI 2.120.0 інша, ніж на хмарному проді; міграції репо
  схему `auth` не описують, тож вирівняти її нам нічим. Тому нічний розклад і типовий ручний запуск — `scope=public`
  (таблиці застосунку; зовнішні ключі на `auth.users` не заважають, бо на час завантаження перевірки вимкнено), а
  `all` — лише явним вибором у Run workflow, щоб перевірити, чи версії вже збіглися. З `all` тренування спершу
  очищає й таблиці `auth.*`, `storage.*`, `private.*` з дампу — роль `postgres` локальної бази може не мати на це прав,
  або на них посилається таблиця поза дампом; тоді помилка в журналі буде про `TRUNCATE`, а не про колонку.

  Що це означає: тренування доводить, що відновлюються дані застосунку, але не акаунти. Рядки `auth.*` (користувачі,
  e-mail, хеші паролів) у копії **є** — `data.sql` у тому самому зашифрованому архіві; job `dump` червоний, якщо в
  `data.sql` немає блоку `auth.users`, і пише в журнал його кількість рядків. Їх відновлюють лише в справжній новий
  проєкт Supabase (розділ «Справжнє відновлення після інциденту»): версія GoTrue хмарного проєкту, ймовірно, ближча
  до проду, ніж у локальному CLI, але може бути й новішою — це не перевірено. Якщо й там падає на `auth.*` — готового
  рецепта немає: не відновлювати `public` окремо (рядки `profiles` посилаються на `auth.users.id`, а нові акаунти
  отримали б інші id), а порівняти колонки таблиць `auth` у `schema.sql` копії і в новому проєкті та вирішувати
  людині. RTO для акаунтів — невідомий (не відрепетирувано); так і записати в `docs/runbook.md`.
- **Строк копії — 7 днів.** Артефакт зникає через тиждень; довшої історії немає. Для довшого зберігання копію треба
  завантажити й покласти в приватне сховище власника (лише `*.gpg`).
- **Free без бекапів.** Інших копій немає: ні щоденних, ні PITR (з тарифу Pro / платне доповнення).
- **Обов'язковий рецензент.** Якщо на `production` увімкнуть обов'язкового рецензента, кожен прогін (і нічний)
  чекатиме схвалення.
- **Гонка з `db-deploy`.** Перевірка версії міграцій до й після дампів ловить міграцію, що завершилась під час
  дампів, але не все: міграція, яку CLI ділить на частини (наприклад, з `CREATE INDEX CONCURRENTLY`), записує версію
  лише наприкінці, тож `data.sql` може вже містити нову колонку, а `schema.sql` — ні. Повне рішення — один advisory
  lock PostgreSQL, який тримають і `dump`, і `db-deploy` (зміна `ci.yml`, окремий PR). Поки його немає, ризик малий:
  `db-deploy` іде лише після злиття PR людиною, а копія — о 01:41 UTC; копію, зняту під час злиття, краще повторити.
- **Тривалість тренування — не RTO.** Job `restore-drill` міряє лише локальне тренування. **RTO** сервісу (скільки
  продукт не працює) охоплює ще новий проєкт, `roles.sql` і `schema.sql`, перемикання Vercel і перевірку — у
  `docs/runbook.md` їх записуємо окремо: тривалість тренування (з прогону) і оцінку RTO.

## Що змінено відносно зразка курсу

- Секрети — у `env` кроків, а не job: `setup-cli`, `upload-artifact` і `download-artifact` їх не бачать.
- Перевірка версії CLI — точно `2.120.0` (не будь-яка 2.x).
- Порожній підсумок рядків `public` у дампі чи в тренуванні — помилка, а не «усе збіглося» з нуля таблиць.
- Невдале розшифрування — зрозуміла помилка; відкриті файли прибираються й тоді, коли job впав.
- Версія міграцій до й після дампів: ловить міграцію, застосовану під час дампів (рев'ю CodeRabbit у PR #100; межі —
  «Обмеження», «Гонка з `db-deploy`»).
- Адреса одноразової бази — з `supabase status`, а не URL із паролем у файлі.
